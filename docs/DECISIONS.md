# 决策记录

采用简短 ADR。日期 2026-10-24；以下是当前工程基线，可在 PR 中修改并说明影响。

## ADR-001：纯软件 OptiLab，先做可信语料闭环

用户已选纯软件路线。暂以编译、仿真、输出校验和可解释报告为方向，避免首版扩展成 CPU、自研编译器和任意代码执行平台。选题名称和研究创新仍允许双方调整，不宣称已确认所有竞赛创新点。

## ADR-002：RV64GC + LP64D + Linux 静态链接

选择 GNU Linux 交叉工具链与 QEMU 用户态，减少裸机启动、sysroot 和硬件依赖。显式固定 ISA/ABI、CPU 型号与 flags；工具版本通过真实实验记录。代价是静态库会影响整体 `.text`，所以另列 kernel 指标。

## ADR-003：固定 O0/O2/Os；按体积推荐

O0 用于观察，O2/Os 用于实用对照。先不做自由 flag 搜索、不将宿主耗时当目标性能。首版推荐固定候选中通过校验且 `.text` 最小者，平局优先 O2、Os、O0；不宣称发明新编译优化算法。

## ADR-004：先定契约，两人并行

建议 yyd 负责核心引擎、sjs 负责界面，可互换。UI 使用明确标记的 mock，真实 API 不回退 mock。公共资产位于 main，成员主动 merge 同步。代码依赖由首个实现 PR 锁定，当前只固定基础检查依赖。

## ADR-005：JSON 证据与 Markdown 文档

开发约定、草稿与实验报告使用 Markdown/JSON，不自动生成 Word/PDF。业务功能尚未实现。项目代码许可证尚未由作者选择，本次不擅自添加。

## 以后如何变更

新增 ADR 编号，写清问题、选择、替代方案、影响文件、版本迁移和验证结果。保留旧 ADR 并标记被哪条替代，避免重写历史。接口破坏变更、换 ISA/ABI、改变优化目标或允许上传代码，都应先有对应决策。
