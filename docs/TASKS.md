# 任务板与里程碑

## 工作量与责任分配

按必需交付的预计工作量分配：**sjs 60%，yyd 40%**。下表权重合计 100，表示开发、模块检查及文档维护的相对工作量，不代表任务数量、代码行数或实际完成率。实际投入偏离估计时重新评估，并同步调整责任和权重。

## 并行开发顺序

| 开发批次 | yyd 工作线 | sjs 工作线 | 对接产物 |
| --- | --- | --- | --- |
| 首批 | ENV-01；ENG-01 执行器和编译/运行适配器 | ENG-03 独立解析；CLI-01 包入口和参数；REPORT-01；GOLD-01 来源登记 | 先按 ARCHITECTURE 的记录包边界实现；双方可各自产生真实 ELF，不等待对方环境 |
| 第二批 | ENG-02 全部用例、记录包和失败路径 | ATTR-01；ENG-04；CLI-01 编排；EVAL-01 统计程序 | 真实 ELF/日志及执行记录包对接；合成输入仅验模块行为 |
| 集成批次 | INTEG-01 按模块复核、运行集成检查并记录差异 | 修复所属模块；补齐报告、评估与演示 | 先验 M0，再验 M1、M2；最终报告等待实际评估 |

sjs 的多项任务是同一负责人的工作队列，不代表这些任务由一人同时完成。优先 ENG-03 与 CLI-01，随后归因与评估；报告和语料准备可在工具链问题排查期间穿插进行。并行目标是消除双方开发启动的串行依赖，最终端到端结果仍须汇合编译执行与分析模块。

## 对接与阻塞处理

1. 首批 PR 固定执行记录包的 Python 类型、调用签名及产物命名，对照 `docs/ARCHITECTURE.md` 的字段边界；兼容性变更附适配方案。类型与编排分别归属，不反复改动同一入口文件。
2. yyd 逐步交付单配置执行器、单样例真实记录、全部配置及失败路径；sjs 逐步交付独立分析、结果组装与 CLI。每次交付均附命令和原始产物位置，不要求一次提交整个模块组。
3. 编排测试可使用显式测试适配器；分析测试可使用合成负例和来源明确的真实 ELF。测试替身不得进入正式 CLI 默认路径，合成 JSON 必须保留 `is_mock: true`，不计入实测。
4. yyd 的环境或执行模块受阻时，sjs 继续独立分析、契约检查、报告和语料工作；sjs 的分析模块受阻时，yyd 继续执行器、用例校验与失败路径检查。记录受阻项、缺少的输入和可继续的任务，不将开发依赖误写为全项目暂停。
5. 真实编译与 QEMU 仍限定 Linux/WSL2；可换用另一真实环境并记录版本。没有可用环境时 M0 标记未完成，不能以 mock 替代。

## 验收与状态管理

- M0：ENV-01、ENG-01/02/03/04、CLI-01、REPORT-01 及相应 INTEG-01 检查；不等待 API/UI。
- M1：ATTR-01 的规则、原始证据、正负例及相应 INTEG-01 检查。
- M2：GOLD-01 双人复核与冻结、EVAL-01、REPORT-02、DEMO-01 及相应 INTEG-01 检查。独立双人标注要求不因主负责人调整而取消。

每项任务登记提交/PR、检查命令及证据位置。模块负责人提交实现和修复，另一成员审阅；不能自审代替复核。完成后更新 STATUS，范围或依赖变化同步对应文档。工作量比例不等于完成率；仅完成 M0 时，归因和独立评估仍列为未完成。

执行模块的调用签名、检查命令、证据位置和后续集成条件见 [EXECUTION.md](EXECUTION.md)；实施计划见 [YYD_EXECUTION_PLAN.md](YYD_EXECUTION_PLAN.md)。
