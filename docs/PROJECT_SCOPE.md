# 项目范围与约束 v0.1

建立日期：2026-10-24，工作时区 Asia/Shanghai。

## 项目定义

暂定名称：RISC-V OptiLab。目标用户是学习或开发 RISC-V 程序的学生，核心问题是：同一程序的编译方案发生变化后，如何验证输出正确、解释目标代码差异，并留下可重复的证据。

当前选题是基于已沟通的纯软件方向建立的工程建议；项目名称、分工与研究创新仍允许双方调整。不能把规划功能写成已实现功能。

## 首版必须有

1. 从注册语料选择一个单文件 C 程序，读取固定输入，不接受任意上传或 shell 参数。
2. 在同一环境按 `-O0`、`-O2`、`-Os` 编译为 RV64GC / LP64D Linux 静态 ELF。
3. 使用 QEMU linux-user 跑完该程序的全部登记用例，以预期 stdout、stderr、退出码进行校验。
4. 展示 `.text` 字节数、整个 ELF 文件字节数、`kernel` 函数机器码字节数、静态指令及压缩指令数量。
5. 从全部用例通过的方案中按 `.text` 最小推荐，明确推荐依据只有静态代码体积。
6. 输出契约一致的 JSON 与 Markdown 报告，含命令、环境、哈希、原始运行结果和失败信息。
7. 前端可以对照查看方案、汇编及解释。mock 模式显著标记，真实模式不回退为 mock。

## 暂不纳入首版

自研 CPU/编译器、完整 ISA 仿真器、RV32/RVV、多线程、浮点精度优化、AI 自动改写源代码、任意用户代码执行、公网多人服务、账户、数据库、硬件验证。一次只运行一个实验，不增加任务队列。

## 技术竞争力如何建立

首版属于工程闭环，不声称“比较几个编译档位”本身是新编译优化算法。后续研究候选是：面向 RISC-V 指令结构的可解释变化分析，以及在正确性约束下的有限编译策略搜索。

要声称改进，需预先确定独立评估语料，至少对比 `-O2`、`-Os` 与固定候选的穷举结果，报告搜索成本、失败率及无收益情况。针对体积的收益只称体积收益。动态指令统计或真实硬件数据未接入前，不声称目标加速、周期下降或能耗下降。

不能将 Ripes、Spike、QEMU、GCC 等第三方成果描述为自研；贡献需明确落实到自己的分析、校验、策略、接口和证据链。
