# 模块架构

## 数据流

浏览器 → FastAPI → 语料注册表 → 编译器适配器 → QEMU 运行器 → 正确性校验 → 静态分析 → 推荐与报告 → 浏览器。

前端开发可以先从 `contracts/examples/` 读 mock。真实模式只使用 API 响应；API 不导入 mock 文件。

## 目录边界

| 目录 | 职责 | 初始状态 |
| --- | --- | --- |
| `backend/app/` | API 与编译、运行、分析、报告模块 | 待实现 |
| `backend/tests/` | 命令构造、错误路径、解析与集成检查 | 待实现 |
| `frontend/` | React/TS 界面、API 客户端、mock 开关 | 待实现 |
| `benchmarks/` | 可信 C 程序、固定输入与预期输出 | 已有首批语料 |
| `config/` | 不由用户自由拼接的编译与运行策略 | 已有基线 |
| `contracts/` | 结果 Schema、接口 mock | 已有契约 |
| `artifacts/` | 每次实验独立目录、ELF、汇编、日志、报告 | 运行后生成，不入 Git |

## 后端分层要求

API 层只校验请求和转换响应。领域层负责实验编排；编译器、QEMU、binutils 分别有独立适配器，不能把整条管线写进一个路由函数。

建议先实现无 HTTP 的 Python 调用入口，再接 API。CLI 命令名称由实现 PR 确定，当前没有可运行的业务 CLI。每个实验使用后端生成的 ID 和独立目录，不信任请求传入的路径。

输出 JSON 必须符合 Schema，Markdown 从同一份 JSON 生成。前端不重新计算正确性结论，不用颜色隐藏失败方案，不把缺失值显示成 0。

## 环境与失败处理

后端运行在 Linux 或 WSL2 的 Ubuntu 24.04 用户空间；Windows 负责编辑器和浏览器。先用工作副本所在 Linux 文件系统完成复现，再考虑跨文件系统性能。工具缺失时返回明确的缺失项，不自动安装或换工具链。

MVP 仅本机协作使用可信语料。QEMU linux-user 将系统调用交给宿主处理，不是任意代码的安全沙箱；如果以后允许上传，必须另作隔离设计并修改范围约束。[QEMU 用户态说明](https://www.qemu.org/docs/master/user/main.html)

编译、工具分析及运行都必须有超时、输出上限、确定的 cwd；使用参数列表及 `shell=False`。Linux 子进程新建进程组，取消或超时时终止并回收整组。每路 stdout/stderr 最大 1 MiB，超限停止；限制必须在读取过程中实施，不能在无限缓冲后才截断。时限见配置。

一个有效实验可以包含失败方案；成功方案仍可展示与推荐。基础设施错误、未知样例、无效请求按 API 契约返回，禁止生成伪造成功结果。
