# 模块架构

## 数据流

浏览器 → FastAPI → 语料注册表 → 编译器适配器 → QEMU 运行器 → 正确性校验 → 静态分析 → 推荐与报告 → 浏览器。

前端初期开发使用 `contracts/examples/` 中的 mock，API 模式使用后端响应。后端 API 与 mock 文件保持独立。

## 目录边界

| 目录 | 职责 | 初始状态 |
| --- | --- | --- |
| `backend/app/` | API 与编译、运行、分析、报告模块 | 待实现 |
| `backend/tests/` | 命令构造、错误路径、解析与集成检查 | 待实现 |
| `frontend/` | React/TS 界面、API 客户端、mock 开关 | 待实现 |
| `benchmarks/` | 可信 C 程序、固定输入与预期输出 | 已有首批语料 |
| `config/` | 固定的编译配置与执行策略 | 已有基线 |
| `contracts/` | 结果 Schema、接口 mock | 已有契约 |
| `artifacts/` | 每次实验独立目录、ELF、汇编、日志、报告 | 运行后生成，不入 Git |

## 后端分层要求

API 层负责请求校验与响应转换，领域层负责实验编排。编译器、QEMU 和 binutils 分别通过独立适配器调用，路由函数不承担工具执行与分析逻辑。

先实现独立于 HTTP 的 Python 调用入口，再接入 API。CLI 命令由实现 PR 定义。每个实验使用后端生成的 ID 和独立目录，请求参数仅允许使用登记的样例 ID。

输出 JSON 应符合 Schema，Markdown 报告由同一份 JSON 生成。前端使用后端给出的校验结论，完整展示成功与失败方案；缺失值以明确的缺失状态显示。

## 环境与失败处理

后端运行在 Linux 或 WSL2 的 Ubuntu 24.04 用户空间，Windows 用于编辑与浏览器访问。参考复现环境将工作副本保存在 Linux 文件系统中。工具缺失时返回缺失项，安装或替换工具链需由开发者明确执行。

MVP 仅在本机执行已登记的可信语料。QEMU linux-user 将系统调用转交宿主处理，因此任意源码上传功能须另行设计执行隔离方案，并更新项目范围。[QEMU 用户态说明](https://www.qemu.org/docs/master/user/main.html)

编译、分析与执行过程均须设置超时、输出上限和工作目录，并使用参数列表及 `shell=False`。Linux 子进程使用独立进程组，取消或超时时终止并回收整组。每路 stdout/stderr 上限为 1 MiB，读取过程中达到上限即停止。时限以配置文件为准。

实验结果可包含失败方案，通过校验的方案仍参与展示与推荐。基础设施错误、未知样例及无效请求按 API 契约返回对应错误。
