# 模块架构

## 数据流

CLI / 可选 FastAPI → 语料注册表 → 编译器适配器 → QEMU 运行器 → 用例校验 → ELF/编码分析 → 整体体积推荐与独立归因 → JSON/Markdown 报告。

前端初期开发使用 `contracts/examples/` 中的 mock，API 模式使用后端响应。后端 API 与 mock 文件保持独立。

## 目录边界

| 目录 | 职责 | 初始状态 |
| --- | --- | --- |
| `backend/app/` | API 与编译、运行、分析、报告模块 | 待实现 |
| `backend/tests/` | 命令构造、错误路径、解析与集成检查 | 待实现 |
| `frontend/` | React/TS 界面、API 客户端、mock 开关 | 待实现 |
| `benchmarks/` | 可信 C 程序、固定输入与预期输出 | 已有首批语料 |
| `config/` | 固定的编译配置与执行策略 | 已有基线 |
| `contracts/` | 结果 Schema、接口 mock | 已有契约 |
| `evaluation/` | 程序家族隔离、对照与验收目标 | 已有计划，语料及实测待建立 |
| `artifacts/` | 每次实验独立目录、ELF、汇编、日志、报告 | 运行后生成，不入 Git |

## 后端分层要求

API 层负责请求校验与响应转换，领域层负责实验编排。编译器、QEMU 和 binutils 分别通过独立适配器调用，路由函数不承担工具执行与分析逻辑。

先实现独立于 HTTP 的 Python 调用入口，再接入 API。CLI 命令遵循 `docs/API_CONTRACT.md`，安装与启动方式由实现 PR 补充。每个实验使用后端生成的 ID 和独立目录，请求参数仅允许使用登记的样例 ID。

输出 JSON 应符合 Schema，Markdown 报告由同一份 JSON 生成。前端使用后端给出的校验结论，完整展示成功与失败方案；缺失值以明确的缺失状态显示。

编码解析器保留字节范围与符号关系；归因器只接受已校验的实验记录及原始产物，按独立策略执行 R001/R002。规则失败不静默改写原实验正确性或推荐，归因状态单独返回。

报告生成器分别读取 `result.json` 和各配置对的可选 `attribution.json`，验证实验 ID、结果哈希、mock 标记与证据引用后渲染。归因策略、评估计划和示例检查位于公共目录，不构成已实现的业务归因引擎。

## 并行实现边界

本节为待实现的内部模块约定，不改变实验/归因 Schema 0.1.0。任务工作量与验收依赖见 `docs/TASKS.md`。各模块的功能职责由既有架构保持，文件责任进一步划分如下：

| 责任人 | 模块边界 | 输入与输出 |
| --- | --- | --- |
| yyd | `backend/app/execution/`、`backend/app/execution_types.py` | 已校验的登记请求与独立工作目录 → 执行记录包；提供通用受限子进程执行器供 binutils 适配器复用 |
| sjs | `backend/app/analysis/` | 真实 ELF 及其哈希 → 原始 binutils 产物、静态指标、编码快照或显式分析失败 |
| sjs | `backend/app/selection/`、`backend/app/attribution/` | 通过校验的配置/指标 → 整体推荐；最终实验记录和证据 → 独立归因结果 |
| sjs | `backend/app/pipeline.py`、CLI、包配置、`backend/app/reporting/` | 调用执行与分析模块、组装实验 JSON、原子保存、归因及报告；维护统一入口和退出码 |

执行记录包至少传递以下内容，具体 Python 类型和调用签名由 yyd 首个执行模块 PR 定义、sjs 复核：

- 实验 ID、UTC 创建时间、请求档位及顺序、基线/语料版本、配置/源码/输入/预期输出哈希。
- 实际工具版本、目标参数和实际使用的 compile/run argv；按配置、用例顺序保留执行结果。
- 每配置的编译是否成功、执行是否全部通过及失败原因，每用例的状态、退出码、原始 stdout/stderr、诊断时间；命令日志和截断/超时信息。
- 编译成功时的 ELF 位置、SHA-256 及原始日志位置；编译失败时 ELF 缺失。产物位置限定在本次实验工作目录内，不能由外部请求指定任意文件。
- 供组装实验 Schema 所需的诊断与 provenance；静态指标、推荐、反汇编和归因由 sjs 模块补充，不由执行模块填入占位值。

记录包是进程内中间结果，不是已完成的 `result.json`，也不新增公开 JSON 契约。原始输出保留字节供严格比较，组装时按既有实验契约表示。内部以“执行通过”区分全流程 `passed`：只有全部用例通过且静态分析成功，才可写入最终 `passed` 和非空 metrics。执行失败分类沿用现有契约；全局基础设施失败按既有 CLI 错误语义处理。

sjs 的分析器必须可独立接收已有 ELF，不强制经完整 CLI 编译生成；测试可在自身 Linux/WSL2 环境按固定基线生成真实产物，记录来源、版本和哈希。合成快照仅验证算术、拒判或呈现逻辑，不声称实际 ELF 解析通过。真实 ELF 和运行产物不入 Git，提交生成说明和检查入口。

受限子进程执行器由 yyd 维护，binutils 适配器由 sjs 维护。执行器未就绪时可对隔离的解析函数使用有出处的固定输出进行检查，正式工具调用必须接入受限执行器后验收。CLI 与归因的单元测试可以注入测试适配器，正式 `run` 默认只能使用真实实现；mock 不作为运行故障的回退路径。

包入口和依赖配置由 sjs 单点维护；yyd 不同时修改 pipeline/CLI。双方按模块分批提交 PR，接口调整同时更新类型、调用方和对应检查，不将公共入口文件作为各自实现的临时存放位置。

## 环境与失败处理

后端运行在 Linux 或 WSL2 的 Ubuntu 24.04 用户空间，Windows 用于编辑与浏览器访问。参考复现环境将工作副本保存在 Linux 文件系统中。工具缺失时返回缺失项，安装或替换工具链需由开发者明确执行。

MVP 仅在本机执行已登记的可信语料。QEMU linux-user 将系统调用转交宿主处理，因此任意源码上传功能须另行设计执行隔离方案，并更新项目范围。[QEMU 用户态说明](https://www.qemu.org/docs/master/user/main.html)

编译、分析与执行过程均须设置超时、输出上限和工作目录，并使用参数列表及 `shell=False`。Linux 子进程使用独立进程组，取消或超时时终止并回收整组。每路 stdout/stderr 上限为 1 MiB，读取过程中达到上限即停止。时限以配置文件为准。

实验结果可包含失败方案，通过校验的方案仍参与展示与推荐。基础设施错误、未知样例及无效请求按 API 契约返回对应错误。
